# GeoServer 2.28.3 → 3.0.2 : Hazelcast 5.7 refusé, adresse client derrière un proxy, catalogue JDBC à la migration

Fiche de montée de version. Natures de source entre crochets : [commit], [runbook],
[notes de version], [notes de dépannage], [mesure] = historique d'une équipe qui a monté
2.28.3 → 2.28.5 → 3.0.1 puis 3.0.1 → 3.0.2 (image dérivée de l'image officielle, plusieurs
réplicas en grappe hz-cluster, catalogue JDBCConfig / JDBCStore sous PostgreSQL, GeoWebCache
sur S3, modules Java maison) ; [code source, relu ici] et [ticket, relu ici] = recontrôlé pour
cette fiche le 2026-11-17 (pom de GeoServer aux tags 3.0.1 et 3.0.2, JIRA) ; [fiche <slug>] =
repris d'une autre fiche de ce dépôt ; [déduction] = ajouté ici, absent de la note.
Un second retour d'expérience de la même montée (2.28.3 → 3.0.1 seulement, puis deux mois
en production) est versé dans la fiche voisine
[montee-2-28-3-a-3-0-1-bascule-et-production](montee-2-28-3-a-3-0-1-bascule-et-production.md) ;
ses points communs avec celle-ci viennent vraisemblablement de la même recette et ne la
confirment pas de façon indépendante.

## Symptôme
1. Réplicas 3.0.2 qui s'arrêtent au démarrage puis bouclent :
   `UnsupportedOperationException: CP subsystem is a licensed feature. Please ensure you have
   an Enterprise license that enables CP`, puis `FATAL: GeoServer failed to deploy`.
   [commit] [mesure]
2. Build de l'image arrêté sur la couche de journaux JSON (`log4j-layout-template-json`)
   après changement de l'image de base. [runbook]
3. Module maison compilé contre `nimbus-jose-jwt` : incohérence de version avec celle de
   GeoServer 3.0.2. [notes de version]
4. Module communautaire JWT Headers 3.0.2 qui refuse la configuration d'un filtre accepté
   en 3.0.1. [commit]
5. 3.0.2 derrière un proxy : `ip.blacklist=<client>` du control-flow ne bloque plus ce
   client, et `ip.<adresse>=N` plafonne tout le trafic du proxy. Lu dans les sources du tag
   par l'émetteur, pas mesuré au banc. [commit] [notes de version]
6. Migration du catalogue JDBC : au **2e** démarrage, `relation "resources" already exists`
   puis contexte Spring arrêté ; ou catalogue 3.0 neuf qui lit les objets du 2.28. [commit]
7. Interface web 3.0.2 derrière un proxy, en http sur un hôte autre que localhost : 403 sur
   chaque action Ajax. [notes de dépannage]
8. Tests qui cassent sans régression : `grep` sur la forme compacte du JSON de
   `GetLegendGraphic` qui ne trouve plus une classe (3.0.1 indente) ; GeoWebCache 3.0.1 qui
   répond **500 « Unknown layer »**, jamais 404, pour une couche sans tile layer. [commit]
   Ni l'un ni l'autre observé par la seconde note (500 non vu, JSON non lu) : à vérifier
   avant de s'y fier. [fiche montee-2-28-3-a-3-0-1-bascule-et-production]
9. Version 2.28.4 épinglée puis abandonnée : modules communautaires pas encore publiés sur le
   dépôt Maven OSGeo ; extensions SourceForge en 404 transitoires. [commit]

## Cause
1. Le pom de 3.0.2 gère Hazelcast **5.7.0** (3.0.1 : 5.3.8) ; hz-cluster construit depuis les
   sources prend cette version, et Hazelcast 5.7 réserve le sous-système CP à la licence
   Enterprise. [commit] [code source, relu ici : `hazelcast.version` aux tags 3.0.1 et 3.0.2]
2. `log4j-layout-template-json` doit avoir la version exacte de `log4j-core` de l'image de
   base (2.26.0 → 2.26.1 entre 3.0.1 et 3.0.2). [runbook]
3. Le pom de 3.0.2 gère `nimbus-jose-jwt` 10.10 (3.0.1 : 10.9.1). [notes de version]
   [code source, relu ici]
4. JWT Headers 3.0.2 refuse un filtre qui valide la signature sans émetteur accepté
   (`validateTokenIssuer`), ou qui prend les rôles d'un en-tête sans qu'on lui ait dit de le
   croire (`trustUnvalidatedRolesHeader`). [commit]
5. GEOS-12235 « Centralize remote IP resolution into a servlet filter » : `X-Forwarded-For`
   n'est cru que depuis `GEOSERVER_TRUSTED_PROXIES` (loopback par défaut) ; les clés `ip=`,
   `ip.blacklist`, `ip.<adresse>` du control-flow portent sur l'adresse du pair (le proxy).
   Lu dans les sources du tag, pas mesuré au banc. [commit] [notes de version] [ticket, relu
   ici : corrigé en 2.27.7, 2.28.6 et 3.0.2]
6. Le schéma du catalogue, créé par un superutilisateur, n'avait pas `USAGE` pour le rôle
   applicatif : PostgreSQL l'a sauté du `search_path`, les tables 2.28 étaient dans `public`.
   Une détection d'idempotence **qualifiée par le schéma** renvoyait NULL au 2e démarrage →
   réinitialisation → table déjà là. Un `currentSchema=<s>,public` fait relire le catalogue
   2.28 par la 3.0. [commit]
7. Wicket 10.11 (3.0.2) : sans en-têtes `Sec-Fetch-*`, la protection CSRF compare
   `Origin` / `Referer` à l'URL vue par Tomcat, qui diffère derrière le proxy. La CSP stricte
   à nonces est aussi celle de 3.0.2. [notes de dépannage]
8. 3.0.1 indente le JSON de `GetLegendGraphic`, et GeoWebCache 3.0.1 répond 500 pour une
   couche sans tile layer : ce sont les tests écrits sur l'ancien format qui cassent. [commit]
9. Les modules communautaires sont publiés après la version officielle. [commit]

## Détection
1. Banc à trois réplicas avec la version de Hazelcast gérée par défaut : arrêt au démarrage.
   [commit] [mesure] `ls WEB-INF/lib | grep hazelcast` donne la version embarquée.
   [déduction]
2. `ls /usr/local/tomcat/webapps/geoserver/WEB-INF/lib | grep log4j-core` dans l'image de
   base. [runbook]
3. Un test de lint compare la version de `nimbus-jose-jwt` du module à celle du pom de
   GeoServer. [notes de version]
4. Avant de monter, relire la configuration de chaque filtre JWT Headers : un filtre qui
   valide la signature sans `validateTokenIssuer`, ou qui prend les rôles d'un en-tête sans
   `trustUnvalidatedRolesHeader`, sera refusé par 3.0.2. La note ne donne ni détection ni
   message d'erreur. [déduction, d'après la cause 4]
5. Comparer, derrière le proxy, l'adresse vue par le control-flow (journal) à
   `X-Forwarded-For`. Non mesuré par l'émetteur. [déduction]
6. Détecter l'idempotence avec le **même `search_path`** que la connexion JDBC, pas par une
   requête qualifiée. [commit] `SELECT has_schema_privilege('<rôle>', '<s>', 'USAGE')`
   (`f` = schéma sauté). [fiche search-path-schema-sans-usage-ignore]
7. Une action Ajax de l'interface par le nom d'hôte public : 403. [notes de dépannage]
8. Comparer le JSON parsé, pas le texte ; attendre 500 « Unknown layer » pour une couche
   sans tile layer. [déduction, d'après le symptôme 8]
9. `curl -I` du jar de chaque module communautaire à la version visée sur
   `repo.osgeo.org` avant d'épingler. [déduction, d'après la cause 9] [mesure du
   2026-11-17 : 200 pour `gs-jdbcconfig` 2.28.4 et 3.0.2, publiés depuis]

## Geste
1. Argument de build `HAZELCAST_VERSION` (vide = version gérée) et épinglage à **5.3.8**,
   celle de 3.0.1 ; suivi de sécurité de 5.3.8 lu avant (CVE-2023-45859 corrigée en 5.3.5,
   CVE-2024-36114 en 5.3.8), à relire à chaque montée. [commit] [runbook] [mesure]
2. Monter `log4j-layout-template-json` avec `log4j-core` de l'image. [runbook]
3. Monter `nimbus-jose-jwt` du module avec GeoServer, dans le même changement.
   [notes de version]
4. Ajouter `validateTokenIssuer` et `trustUnvalidatedRolesHeader` à la configuration du
   filtre. [commit]
5. Déclarer la plage du proxy dans `GEOSERVER_TRUSTED_PROXIES` avant de compter sur une
   règle `ip.*` du control-flow derrière un proxy. [commit] [notes de version]
6. Catalogue : `ALTER SCHEMA … OWNER` ou `GRANT USAGE, CREATE` au rôle applicatif
   [fiche search-path-schema-sans-usage-ignore] ; `currentSchema=<s>` **sans** `,public`. La migration du répertoire de données 2.28 → 3.0
   est **irréversible** : sauvegarder catalogue et volume ; le passage s'est fait sur un
   catalogue neuf dans un schéma séparé et un volume neuf, retour arrière = revenir à
   l'image 2.28. Recoupe [search-path-schema-sans-usage-ignore](../postgis/search-path-schema-sans-usage-ignore.md).
   [commit]
7. Pistes notées, **non appliquées** : `-DGEOSERVER_CSRF_WHITELIST=<hôtes>` (hôte seul), ou
   `RemoteIpValve` avec `hostHeader="X-Forwarded-Host"` ; `-Dorg.geoserver.web.csp.strict=false`
   passe la CSP en report-only. [notes de dépannage]
8. Réécrire les tests sur le JSON parsé et sur le code 500 de GeoWebCache.
   [déduction, d'après le symptôme 8]
9. Épingler une version seulement quand ses modules communautaires sont publiés ;
   `curl --retry` pour SourceForge. Recoupe
   [modules-communautaires-version-exacte](modules-communautaires-version-exacte.md). [commit]
10. Marches : 2.28.3 → dernier 2.28.x (2.28.5) avant le saut en 3.0 ; puis 3.0.1 en changeant
    ensemble `GS_VERSION` de l'image, `geoserver.version`, `gwc.version`, `spring.version`,
    `geotools.version` des poms des modules maison, extensions et modules communautaires de
    la même version. [commit] Dans la seconde note, 2.28.5 n'a été construite et démarrée
    qu'en local, la production est passée de 2.28.3 à 3.0.1 en une fois : le palier n'y a
    rien prouvé en exploitation. [fiche montee-2-28-3-a-3-0-1-bascule-et-production]
11. Modules Java maison : **aucun changement de code** en 3.0 (pas de `javax.servlet`, API
    Spring / GeoTools / GeoWebCache appelées stables), recompilation seule ; une
    transformation de rendu raster satisfait le contrat `RenderingProcess` de GeoTools 35.1
    par `invertGridGeometry` (`invertQuery` n'est appelé que pour une source vecteur), rendu
    identique au pixel près face à 2.28. Recoupe
    [transformation-raster-coverage-source-non-injecte](transformation-raster-coverage-source-non-injecte.md).
    [commit]
12. Rendu raster passé de JAI à **ImageN** en 3.0 : rejouer tous les tests de couches et
    d'animation. [commit]
13. Grappe : `--add-modules java.se --add-opens …` sous Java 21, `ignoreDirs=…,cluster` dans
    `jdbcstore.properties`, nom de grappe portant la version (2.28 et 3.0, ou 3.0.1 et 3.0.2,
    ne partagent pas un bus d'événements) ; une montée n'est donc pas roulante : réplicas
    arrêtés ensemble (`Recreate`). Recoupe
    [grappe-hazelcast-config-et-jdbcstore](grappe-hazelcast-config-et-jdbcstore.md).
    [commit] [runbook]
14. Épingler chaque artefact : version, commit du tag (hz-cluster cloné à ce commit), digest
    de l'image de base (build arrêté si elle n'a pas `gs-main-<version>.jar`), sha256 de
    chaque zip et jar (JDBCConfig, JDBCStore, control-flow, gwc-s3, WPS, JWT Headers).
    [runbook]
15. Les scripts SQL de JDBCConfig / JDBCStore ne s'exécutent qu'au **premier** démarrage :
    comparer ceux des deux versions avant de monter (identiques entre 3.0.1 et 3.0.2) ; s'ils
    diffèrent, le retour arrière devient une restauration. [runbook]
16. Les hypothèses sur l'intérieur de hz-cluster (événements des autres réplicas rejoués sur
    des threads `HzSynchronizer-<n>`, traités seulement à partir de `ContextLoadedEvent`) ne
    préviennent pas quand elles changent : un test lit les sources du module à la version
    cible et nomme l'hypothèse rompue. [runbook]
17. Spring et jackson-databind des modules maison (7.0.8, 2.22.0) ne suivent pas seuls ceux
    de l'image 3.0.2 (7.0.9, 2.22.2) : écart de patch sans contrôle automatique.
    [runbook] [code source, relu ici : `spring.version` 7.0.9 au tag 3.0.2]
18. Un provisionnement (styles, couches) lancé pendant le redémarrage des réplicas peut
    trouver un catalogue partiel ; un délai côté client n'annule pas la requête serveur :
    provisionnement non destructif (comparer, puis écrire), relecture après écriture, échec
    visible. [commit]
19. Le marqueur de version écrit dans le catalogue garde la version qui l'a **créé**, pas
    celle qui tourne. [runbook]
20. Après la montée, **sur chaque réplica** (pas via le Service) :
    `/geoserver/rest/about/version.json`, `/geoserver/rest/layers.json` (mêmes couches), un
    GetMap. Mesuré au banc (3 réplicas, 116 objets de catalogue, 26 couches, un
    GetCapabilities toutes les 0,5 s) : 3.0.1 → 3.0.2 en 115 s dont **61,8 s** de 502 ;
    retour en 120 s dont 63,6 s ; schémas, objets et couches inchangés. Non mesuré : schéma
    modifié, autre paire de versions, gros catalogue, écritures pendant l'arrêt. [mesure]
    [runbook]
21. Le `context.xml` de Tomcat est passé tel quel sous Tomcat 11 (syntaxe acceptée). [commit]
    Attention : dans l'image officielle, le `conf/context.xml` global est **ignoré** par le
    `<Context override="true">` du `server.xml` ; « passé tel quel » ne prouve pas qu'il soit
    lu. Voir [image-officielle-context-xml-ignore-jndi](image-officielle-context-xml-ignore-jndi.md).
    [déduction] La seconde note dit aussi « compatible Tomcat 11 tel quel », sans avoir
    vérifié qu’il soit lu. [fiche montee-2-28-3-a-3-0-1-bascule-et-production]
